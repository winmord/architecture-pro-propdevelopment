# Отчёт по результатам анализа Kubernetes Audit Log

## Подозрительные события

### 1. Доступ к секретам:
  - Кто: system:serviceaccount:secure-ops:monitoring
  - Где: namespace kube-system
  - Почему подозрительно:
    ServiceAccount из другого namespace получил доступ к secrets kube-system.
    Это нарушение принципа least privilege и потенциальная утечка токенов.

### 2. Привилегированные поды:
  - Кто: пользователь (kubectl client / admin context)
  - Комментарий:
    Был создан pod с securityContext.privileged=true.
    Это позволяет контейнеру получить полный доступ к ноде.
    Считается критической уязвимостью.

### 3. Использование kubectl exec в чужом поде:
  - Кто: пользователь с правами exec
  - Что делал:
    Выполнял команды внутри pod в namespace kube-system (coredns).
    Это может использоваться для lateral movement.

### 4. Создание RoleBinding с правами cluster-admin:
  - Кто: пользователь (kubectl apply)
  - К чему привело:
    ServiceAccount monitoring получил права cluster-admin.
    Это фактически полный контроль над кластером.

### 5. Удаление audit-policy.yaml:
  - Кто: admin
  - Возможные последствия:
    Отключение аудита — попытка скрыть следы.
    Это один из самых критичных индикаторов компрометации.

## Вывод

В кластере зафиксирована последовательность действий, характерная для атаки:

- Получение доступа к секретам
- Эскалация привилегий
- Доступ к системным подам
- Попытка отключения аудита

Основные проблемы:
- Некорректно настроенный RBAC (избыточные права)
- Отсутствие ограничений на privileged pods
- Нет политики ограничения exec
- Audit policy может быть удалена

Кластер считается скомпрометированным.

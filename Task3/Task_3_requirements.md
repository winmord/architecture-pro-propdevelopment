# Требования к внешней интеграции с партнёром «Умный дом»

PropDevelopment внедряет два сервиса «Умный дом» через внешнего партнёра:
- Интеллектуальный домофон (видеодомофон + открытие по биометрии/лицу)
- Интеллектуальный шлагбаум (управление + распознавание номеров автомобилей)

Сервисы должны быть доступны через мобильное приложение собственников PropDevelopment.

Данный документ описывает требования к безопасности, протоколы аутентификации/авторизации и схему взаимодействия между системами PropDevelopment и внешней платформой партнёра.

---

## 1. Требования к безопасности

| № | Требование | Обоснование |
| -- | ---------- | ------------ |
| 1 | **Mutual TLS (mTLS)** для всех вызовов API между PropDevelopment и партнёром. | Предотвращает подмену сервера, обеспечивает аутентификацию обеих сторон и защиту от Man-in-the-Middle. |
| 2 | **Шифрование данных в транзите** (TLS версии 1.3 и выше). | Биометрические данные (хеши лиц), номера автомобилей и логи доступа являются персональными или чувствительными данными. |
| 3 | **Подпись запросов** (HMAC-SHA256) или использование JWT с коротким временем жизни (TTL не более 5 минут). | Дополнительная защита от replay-атак и подделки запросов. |
| 4 | **Логирование всех интеграционных вызовов** на стороне PropDevelopment с фиксацией: timestamp, ID запроса, метод, результат (успех/ошибка), IP-адрес партнёра. | Необходимо для аудита безопасности, расследования инцидентов и соответствия законодательству (РФ, 152-ФЗ). |
| 5 | **Ограничение скорости (rate limiting)** для API партнёра: не более 100 запросов в минуту на один метод. | Защита от случайных или намеренных DDoS-атак, а также от ошибок в интеграции. |
| 6 | **Валидация входящих webhook** от партнёра: проверка подписи (HMAC) и источника по списку разрешённых IP-адресов. | Предотвращает подмену уведомлений о событиях (открытие двери, проезд). |
| 7 | **Хранение биометрических данных** только в виде **соли и хеша** (bcrypt или Argon2). Исходные изображения лиц не передаются и не хранятся. | Минимизация рисков при потенциальной утечке данных. |
| 8 | **Политика автоматического удаления логов доступа** старше 90 дней. | Соответствие требованиям законодательства о хранении персональных данных и журналов событий. |
| 9 | **Регулярное тестирование безопасности** интеграции (пентест) не реже 1 раза в год. | Выявление уязвимостей в API партнёра до того, как их найдут злоумышленники. |

## 2. Протоколы аутентификации и авторизации

### 2.1. Направление: PropDevelopment → Партнёр (отправка команд)

| Параметр | Значение |
| -------- | -------- |
| **Протокол** | OAuth 2.0 (Client Credentials flow) + mTLS |
| **Описание** | Сервис `tenant-core-app` запрашивает `access_token` у партнёра, используя client_id и client_secret, переданные по защищённому каналу. Токен имеет ограниченный скоуп `smart_home:command`. |
| **Срок действия токена** | Не более 1 часа, с возможностью автоматического обновления. |
| **Передача токена** | В HTTP-заголовке `Authorization: Bearer <token>`. |

### 2.2. Направление: Партнёр → PropDevelopment (webhook-уведомления)

| Параметр | Значение |
| -------- | -------- |
| **Протокол** | Подпись запроса (HMAC-SHA256) |
| **Описание** | Партнёр вычисляет HMAC от тела запроса + timestamp + уникального ID события и передаёт в заголовке `X-Signature`. PropDevelopment проверяет подпись по предварительно переданному симметричному ключу. |
| **Защита от повторов** | Проверка временной метки `X-Timestamp` (допустимое отклонение ±5 минут) и уникальности `X-Event-Id`. |

### 2.3. Направление: Мобильное приложение → API Gateway PropDevelopment

| Параметр | Значение |
| -------- | -------- |
| **Протокол** | OAuth 2.0 (Authorization Code Flow) + JWT |
| **Описание** | Собственник аутентифицируется в `auth-service-1` (Keycloak). Полученный JWT-токен передаётся в API Gateway, где проверяется подпись, срок действия и права доступа. |
| **Авторизация команд** | RBAC на стороне PropDevelopment. `tenant-core-app` проверяет, что собственник имеет право на управление конкретным домофоном (по привязке к квартире) или шлагбаумом (по привязке к автомобилю). |

## 3. Организация взаимодействия между системами

**Общая схема:**
Мобильное приложение собственника → API Gateway PropDevelopment → сервис tenant-core-app → внешний партнёр «Умный дом». Обратно: партнёр отправляет webhook-уведомления на API Gateway.

**Синхронное взаимодействие (команды)**

Когда собственник в мобильном приложении нажимает «открыть дверь» или «поднять шлагбаум», запрос идёт через API Gateway в tenant-core-app.
tenant-core-app проверяет права пользователя (есть ли у него доступ к этой двери или авто) и, если всё в порядке, вызывает REST API партнёра.
Вызов защищён mTLS и OAuth2 (Client Credentials). Партнёр выполняет команду и возвращает статус. Ответ идёт обратно к приложению.

**Асинхронное взаимодействие (уведомления)**

Партнёр самостоятельно уведомляет PropDevelopment о событиях, которые произошли на оборудовании (например, «дверь открыта по лицу», «автомобиль с номером Х проехал через шлагбаум»).
Уведомление приходит в виде webhook (HTTP POST) на специальный эндпоинт API Gateway.
Заголовки запроса содержат подпись (HMAC) для проверки подлинности, уникальный ID события и временную метку.
API Gateway проверяет подпись, после чего передаёт событие в tenant-core-app для обработки (логирование, возможно, отправка push-уведомления собственнику).
